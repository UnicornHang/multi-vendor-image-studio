# 漫画制作 Agent 产品方案落地评审

评审日期：2026年11月23日。对象：漫画制作 Agent 产品需求与实施方案 1.0。状态：有条件可实施，产品基线等待用户确认。

## 评审结论

方案在模块划分和数据可靠性方面可实施，但完整P0同时包含制作工作流、漫画编辑器和任务平台，范围偏大。建议先以三页作品验证核心生产闭环，再扩展管理与自动修复功能。当前尚无真实样章证明角色一致性与整页观感达到目标，不应把基础生图成功等同于漫画生产可用。

现有代码检查确认：shared/adapters/profiles.js中的通用OpenAI兼容及多个其他模式声明reference为false；MiniMax模式传入单项subject_reference；自定义模板暴露单个refBase64。这说明当前集成尚未建立“多个角色分别绑定多个参考图”的完整契约，不代表这些厂商当前服务端一定不支持。实际能力应以所用模型、接口和样张验证为准。

## 必须在开发前解决的问题

### 双角色参考与身份绑定

方案以两名角色的样章作为验收，但底层仍以单个ref对象为核心。应增加ReferenceBinding，记录assetId、用途、characterId、优先级和输入顺序，定义不同渠道如何编译。多参考不支持时，联系用户选择经验证的合成设定图或文本降级方案；不得默认拼接多张图即可保持身份。

样张需覆盖同框双人、侧脸、反打、近景与道具互动。只比较单人正面图不足以验证漫画需求。

### 自动执行与人工选图冲突

现方案要求用户选定角色和候选，又提供自动整章制作，未定义自动选择规则。建议首发以分阶段制作为默认，明确三个检查点：剧本设定、分镜、成品。自动模式在未配置自动选用规则时停在候选选择，不宣称全自动完成。

若用户更看重快速预览，可允许首个成功候选临时用于草稿，审核状态保持unchecked；正式导出仍需满足检查要求。

### 参考漫画效果与生产路线的匹配

逐格生成能改善可编辑性，却增加整页光影、空间、色彩和人物比例不统一的风险。程序合成并不能自行保证画面连贯。应先制作一页双人对白与一页动作反应的对照样张，分别验证逐格合成和整页草稿。

正式路线以用户对样张的判断为准。若用户核心诉求是接近参考图的整页观感，整页路线可能需要提前；若核心诉求是台词和单格精修，则维持逐格路线。

### 生图能力与修改承诺

缺少imageEdit和maskEdit时，“只改表情，其他不变”不能作为生图结果保证。P0应将其描述为“以保留其余设定为目标重新生成候选”，并保留原图。其他分镜不改变可以通过版本隔离保证；当前格的其余像素完全不变则需要额外能力验证。

### 质量评价需要补齐操作口径

原文的每项均分1.5不能抵消关键格剧情错误。增加一票否决项：角色身份互换、关键道具错误、关键台词遗漏或说话人错误、阅读顺序错误。固定测试脚本、镜头与评审人，保留修复前后记录，并统计每格尝试次数和人工操作耗时，避免以无限重绘换取通过。

## 可由研发验证的问题

字体度量和后端渲染必须先做样机。前后端共用换行结果并不自动确保字体版本、字形和输出一致，需要固定字体文件与渲染参数并验证导出图。

任务系统需补充结果已返回但尚未落盘、取消与返回同时发生、重启与租约续期冲突等故障点。不能保证上游恰好执行一次时，依靠待核对状态防止自动重复收费。

API清单是方向，尚非可直接联调的接口规范。进入开发前需补充完整请求和响应schema、分页、对象删除、资产库CRUD、版本恢复、选择候选、问题处理及异步完成事件。明确run的父子任务汇总与partial failure展示，避免单格失败导致整体状态含糊。

备份、凭证和缓存边界需要确定：credentialRef必须指向可重启后恢复的服务端配置；使用浏览器临时密钥时，重启后的任务应进入等待配置，而不是继续带空密钥调用。

预算应同时限制候选数量与调用次数。一次请求可能产出多张图，不能把一次调用与一张图等价。金额上限应涵盖文本、视觉与图片调用；无法估算时只承诺调用数限制。

## 建议调整的交付范围

第一步交付技术样章：固定故事、两名角色、一个主场景、三页作品。先验证效果和成本，再确定模型、路线与用户接受的人工干预。

第二步交付最小工作流：项目持久化、角色参考、分镜列表、基础矩形组版、独立台词、单格生成与候选选择、后台任务恢复、PNG导出与基础备份。

第三步扩展完整编辑器：精细拖拽、复杂气泡、自然语言定位修改、资产库管理、问题清单和批量功能。项目完整恢复及预算硬限制仍须在面向真实生产的首发中完成，不能因阶段拆分而删除。

整页草稿是否提前取决于用户体验偏好及样张结果。有限自动修复、复杂斜切、跨作品共享及长篇检索延后。

## 需要用户确认

1. 本地自用、线上工具还是商业产品。原方案的本地单用户是工作假设，并非用户已确认的需求。
2. 优先分阶段精修、自动整章还是快速整页预览。该选择影响默认工作流及两条生成路线的优先级。
3. 实际生图渠道、模型及参考图编辑效果。仅需名称与效果，不需要密钥。
4. 一章页数、可接受的人工干预、单章费用、开发人员与时间限制。原六个周迭代以两名全栈及兼职设计测试为假设，不适用于未知人员配置。

## 后续决策

收到上述确认后，将原PRD更新为明确的P0功能、延后项及能力验证清单。所有模型相关承诺以样张验证为前置条件，研发负责的常规实现选择无需用户逐项决定。
